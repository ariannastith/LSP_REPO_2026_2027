# Design Evaluation — `CourseRegistration`

Arianna Stith · CSCI 363 Midterm, Question 2, Part 1

The given `CourseRegistration` class is a god class. Arthur Riel’s Heuristic 3.2 says not to create god classes, and Heuristic 2.8 says a class should capture one and only one key abstraction. This class is trying to be a student, a course, a tuition policy, a file store, an email client, and a logger at the same time. The name even advertises that mix: “course registration” is a process, not a single domain concept, and `registerStudent()` is one method that performs every step of that process.

The data members make the same problem visible. `studentId`, `studentName`, and `email` belong to a student. `courseCode` and `creditHours` belong to a course. Nothing in the class represents a registration record as its own object. Heuristic 2.9 says to keep related data and behavior in one place; Heuristic 2.10 says to spin off non-related information into another class. Tuition math uses `creditHours` but not `email`. The “send confirmation email” line uses `email` but not `creditHours`. The file write uses `studentId`, `courseCode`, and `tuition` but not `studentName`. That is noncommunicating behavior (Heuristic 3.4): different methods, or different parts of the same method, each operate on a proper subset of the fields. When behavior stops using most of the data most of the time, the class is doing too many jobs.

Encapsulation is also missing. Heuristic 2.1 says all data should be hidden within its class. Every field here is `public`, there is no constructor, and there is no validation. A caller can set `creditHours` to a negative number, leave `email` null, or change `courseCode` after a registration has already been written to disk. Because the fields are public, the class cannot protect its own invariants, and any later redesign has to chase every place that touched those fields directly.

The method itself is procedural rather than object-oriented. Heuristic 3.1 says to distribute system intelligence horizontally so that the top-level classes share the work. Here the intelligence is vertical: one method calculates tuition (including a hardcoded $750 rate and a 10% heavy-load discount), prints a confirmation, appends a CSV line to `registrations.txt`, pretends to send email by printing to standard output, and logs a timestamp. I/O, money rules, and domain data are fused together. That is bad for maintainability because a change to tuition policy, storage, or notification all edit the same method. It is bad for extensibility because there is no object to replace if the university later stores registrations in a database or sends a text instead of an email. It is bad for correctness because the `FileWriter` is left to a bare `catch (Exception)` that only prints a stack trace, so a failed save still “sends” a confirmation and still logs success.

A smaller but related issue is that `CourseRegistration` depends on concrete mechanisms (`FileWriter`, `System.out`, `Date`) instead of on collaborators that own those responsibilities. Heuristic 4.1 says to minimize the number of classes with which another class collaborates, which sounds as if a single class is simpler, but the heuristic is about *accidental* coupling, not about stuffing every dependency into one file. The current class is coupled to the file system, the console, and a specific tuition formula. Those couplings will spread into every test and every future feature.

In short, the design fails Riel’s tests for a single abstraction, hidden data, related data-and-behavior, and distributed intelligence. The next two parts propose a CRC design that splits those responsibilities into classes that can change independently.
