# Evolving Requirements and Design Rationale

Arianna Stith · CSCI 363 Midterm, Question 2, Part 3

The new requirements are two storage options (local file or database, chosen by deployment environment) and two confirmation channels (email or text message). The CRC design already put those two concerns in `RegistrationStore` and `ConfirmationSender`, so the process class does not have to change its responsibilities.

For storage, I would keep the `RegistrationStore` card and add two implementing collaborators: `FileRegistrationStore` (append a line to a local file) and `DatabaseRegistrationStore` (insert a row). `RegistrationService` still collaborates with `RegistrationStore`; it does not collaborate with `FileWriter` or with a database API. The deployment environment chooses which store object to hand the service. That is the change I would make to the CRC cards: `RegistrationStore` stays the collaborator on the service card, and the two concrete stores list `Registration` as their collaborator and `RegistrationStore` as the abstraction they fulfill. I would not put “save to file or database” on `Registration` or on `RegistrationService`, because then both storage options would leak back into the god-class problem from Part 1.

For confirmations, I would do the same split on `ConfirmationSender`: `EmailConfirmationSender` and `TextConfirmationSender`. `Student` already owns the contact information, but `Student` should not own sending. A student is not a mail server or an SMS gateway. `ConfirmationSender` uses the student; the student does not use the sender. `RegistrationService` still just asks its sender to notify the student after a successful save.

The important ownership decision is that **`RegistrationStore` owns persistence, and `RegistrationService` does not.** The original class buried `new FileWriter("registrations.txt")` inside `registerStudent()`, which is why a database requirement would have forced a rewrite of the only method in the system. In the CRC design, the service’s responsibility is the *order of the registration process* (calculate, record, save, notify, log). The store’s responsibility is *how a record is written*. If the environment is a laptop, the file store is injected; if the environment is the registrar’s server, the database store is injected. Either way, `Student`, `Course`, `TuitionCalculator`, and `Registration` stay the same. That matches Heuristic 2.8 (one abstraction per class) and Heuristic 2.9 (related data and behavior together): file-format details live with the file store, not with tuition, and not with the student.
